regressions. This phase establishes a true enterprise multi-user and multi-tenant

2. USER IDENTITY & HIERARCHY ARCHITECTURE
--------------------------------------------------------------------------------
The platform enforces a clean tripartite identity model:

A. ROLES (Authority & Administrative Permissions):
   - PLATFORM_OWNER: Highest permanent authority (lingga_admin). Cannot be deleted
     or demoted.
   - SUPERADMIN / PLATFORM_SUPER_ADMIN: Full platform administration.
   - ADMIN: Standard platform administrative staff.
   - NOC_OPERATOR / NETWORK_ENGINEER / NOC_ANALYST: Operational roles.
   - USER: Standard registered customer account.
   - GUEST: Anonymous visitor identified via ephemeral X-Guest-ID.

B. PLANS (Subscription Tiers):
   - FREE: Default tier for new accounts, standard token allotment.
   - PRO: Professional engineering tier with higher quotas.
   - ENTERPRISE: Highest quota tier with custom limits and SLA.

C. ENTITLEMENTS (Feature Flags):
   - NETWORK_PLUS (networking_plus): Authorizes access to operational network
     features (topology viewer, device inventory, playbook execution, NMS telemetry).
     Only users with this active entitlement or PLATFORM_OWNER can interact with
     network infrastructure.

D. Bootstrap Superadmin Idempotency:
   - "bootstrap_superadmin()" guarantees that re-running provisioning never corrupts
     data, resets active sessions, or removes PLATFORM_OWNER role assignments.

3. MULTI-TENANT DATA ISOLATION & WORKSPACE PARTITIONING
--------------------------------------------------------------------------------
A. Chat Sessions Isolation:
   - Chat sessions ("chat_sessions.py") and turns are bound to "user_id".
   - Guests receive isolated sessions prefixed with their unique "X-Guest-ID".
   - Cross-user retrieval, updating, or deletion returns HTTP 404 Not Found.

B. Multi-Tenant Network Workspaces:
   - Introduced "network_workspaces" table in SQLite schema.
   - Automatically provisions an isolated default workspace per user upon registration.
   - Topology devices, operational incidents, SLA configs, and playbooks are mapped
     to "workspace_id" and "user_id".
   - "WorkspaceService" strictly scopes queries so User A cannot interact with
     User B's devices, routers, or network topologies.

--------------------------------------------------------------------------------
4. PER-USER MEMORY ARCHITECTURE
--------------------------------------------------------------------------------
A. Service: "UserMemoryService" ("core/tenant/memory_service.py")
B. Storage: "user_memories" & "user_preferences" tables.
C. Features:
   - Strict Logical Scoping: Every memory record has an immutable "user_id".
   - Classification Categories: learning, technical, project, communication,
     workflows, general.
   - Importance Scoring: Real-valued scale (0.0 to 1.0) with automated normalizer
     for UI inputs (0-100).
   - Global Memory Toggle: Users can toggle AI memory recall ON/OFF anytime in Settings.
   - Purge & Bulk Operations: Clear all memories without affecting other tenants.
   - Dual Router Support: Both singular (/memory) and plural (/memories) endpoints.

--------------------------------------------------------------------------------
5. PER-USER PERSONA ARCHITECTURE
--------------------------------------------------------------------------------
A. Service: "UserPersonaService" ("core/tenant/persona_service.py")
B. Storage: "user_personas" table with system presets seeded on schema migration.
C. 5 Immutable System Presets:
   1. preset_general    : AIRA Default Assistant (balanced, polite, adaptive).
   2. preset_technical  : Senior Network Infrastructure Specialist (dense CLI/RFC).
   3. preset_tutor      : Step-by-step Engineering Mentor (pedagogical, diagnostic).
   4. preset_consultant : Strategic Enterprise Architect (cost, SLA, risk-focused).
   5. preset_custom     : User Configurable Template.
D. Custom Persona Rules:
   - System presets are READ-ONLY; deletion or modification attempts return HTTP 400/403.
   - Duplication/Cloning: Users can clone any system preset into a custom persona.
   - Independent Active Persona: Each user selects their active persona independently.
   - Dynamic Preview: Users can preview prompt generation without saving changes.

--------------------------------------------------------------------------------
6. CONTEXT COMPOSITION ORDER & SAFETY GUARDRAILS
--------------------------------------------------------------------------------
Context assembly in "core/context/builder.py" strictly follows the prioritized order:

   [1] SYSTEM CORE RULES (Immutable security boundary, tool execution ethics, safe defaults)
   [2] PLATFORM INSTRUCTIONS (AIRA identity, environment parameters)
   [3] ACTIVE PERSONA (Response style, tone, terminology, depth instructions)
   [4] RELEVANT USER MEMORY (User preferences, historical technical context)
   [5] CONVERSATION HISTORY (Previous turns in active session)
   [6] USER MESSAGE (Current user query)

Safety Assurance:
- Persona instructions and long-term memories are inserted strictly BELOW System
  Core Rules.
- Prompt injection or jailbreak attempts via persona custom instructions cannot
  override system safety rules, approval gates, or operational permission checks.

7. NETWORK++ ENTITLEMENT GATING
--------------------------------------------------------------------------------
All 8 networking routers in "AIRA_ECOSYSTEM/api/routers/" are protected by
FastAPI dependencies using "require_network_plus":

   1. /api/devices             (Device management & inventory)
   2. /api/topology            (Topology graph & visualization)
   3. /api/nms/*               (NMS telemetry & monitoring)
   4. /api/v1/playbooks        (Ansible-compatible network playbooks)
   5. /api/v1/gateways         (Edge operational gateways)
   6. /api/operations/*        (Incidents, maintenance, tickets)
   7. /api/intelligence/*      (Network intelligence & analytics)
   8. /api/v1/decisions        (Autonomous routing & optimization decisions)

Gating Enforcement:
- Non-entitled users (Free plan without add-on) receive HTTP 403 Forbidden:
  {
    "detail": {
      "code": "ENTITLEMENT_REQUIRED",
      "message": "Fitur ini memerlukan entitlement Network++ aktif.",
      "required_entitlement": "NETWORK_PLUS"
    }
  }
- Guests receive HTTP 401 or 403.
- Entitled users (Network++ active) and PLATFORM_OWNER are granted immediate access.

--------------------------------------------------------------------------------
8. ADMIN SITE AUTHORIZATION
--------------------------------------------------------------------------------
- Admin Site API endpoints under "/api/v1/admin/*" are restricted strictly to
  users with internal administrative roles (PLATFORM_OWNER, SUPERADMIN, ADMIN).
- Regular users (even those with PRO or Network++ entitlements) calling
  administrative endpoints receive HTTP 403 Forbidden.
- Platform Owner ("lingga_admin") maintains unrestricted access to manage users,
  view platform-wide audit logs, and assign subscriptions.
