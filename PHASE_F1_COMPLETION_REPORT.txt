1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Phase F.1 successfully simplified the architecture of AIRA OS. All legacy
concepts related to subscription plans (Free/Pro/Enterprise), payment, billing,
plan-based feature entitlements, and token-based access blocking were eliminated.
Tokens now function strictly as internal telemetry for performance and cost
observability, never as operational gates.

The platform now operates on an enterprise-grade model:
AIRA OS -> Organization -> Users -> Groups -> Permissions

All interactions require mandatory username/password authentication. Guest mode,
anonymous access, and guest bypasses have been completely removed. Network
infrastructure (devices, topology, NMS, playbooks, wiring) belongs to the
organization and is shared among all authorized users without artificial silos.
Simultaneously, chat conversations, personas, and memory remain strictly
isolated per user.


2. MANDATORY AUTHENTICATION & SESSION MANAGEMENT
--------------------------------------------------------------------------------
- Zero Guest / Anonymous Mode: Any request lacking a valid Bearer token returns
  HTTP 401 Unauthorized across all endpoints (/api/devices, /api/topology,
  /api/sessions, /api/chat, /api/v1/admin/*).
- Standard Username & Password: Login via POST /api/v1/auth/login validating
  against scrypt/PBKDF2 hashes in operational_users.
- Account State Enforcement: If an account is disabled (account_enabled = 0),
  active sessions are immediately revoked and further logins are rejected
  with HTTP 401/403.
- Heartbeat Tracking: Frontend reports active presence every 30 seconds to
  POST /api/v1/auth/heartbeat, maintaining real-time ONLINE status.


3. MIKROTIK-STYLE GROUP-BASED ACCESS CONTROL (RBAC)
--------------------------------------------------------------------------------
- Canonical Permission Registry: 43 granular permissions structured as
  module.resource.action across all domains (devices, inventory, topology,
  nms, config, playbooks, automation, admin, audit, system).
- Conflict Resolution Principle: Explicit DENY strictly overrides ALLOW.
  If a user belongs to multiple groups where one ALLOWs and another DENYs
  a permission, the effective permission evaluates to FALSE.
- Superadmin Privilege: Users belonging to SUPER_ADMIN automatically possess
  all 43 permissions regardless of individual denials.
- System Default Groups:
  1. SUPER_ADMIN: Full platform, identity, and infrastructure control.
  2. ADMIN: Infrastructure management, user management, and playbook execution.
  3. NETWORK_ENGINEER: Device management, config deploy, topology edit, playbooks.
  4. NOC: Read-only inventory, topology, NMS alerts, and diagnostic commands.
  5. SOC: Security audit logs, incident inspection, read-only topology.
  6. READ_ONLY: Viewer access across monitoring and topology without modifications.
- Custom Groups & Multi-Membership: Administrators can create, edit, duplicate,
  and delete custom groups with granular ALLOW/DENY/NONE assignments per permission.


4. BACKEND-ENFORCED AI TOOL & API AUTHORIZATION
--------------------------------------------------------------------------------
- AI Tool Interception: In core/orchestrator.py, Orchestrator._execute_tool
  inspects the active user context from current_event_scope() and queries
  rbac_service.has_permission(user_id, required_perm).
  If permission is lacking, tool execution is immediately aborted with a
  descriptive "Permission Denied" error message.
- Parity with REST APIs: Direct REST endpoints enforce identical permission
  dependencies (e.g. inventory.create, config.apply, playbooks.execute),
  guaranteeing that neither conversational AI nor direct API calls can bypass
  security policies.


5. DATA OWNERSHIP & MULTI-TENANT ISOLATION MODEL
--------------------------------------------------------------------------------
- Organization-Owned Operational Resources (Shared):
  * Network Devices & Credentials
  * Topology Nodes, Edges, Links, and Physical Wiring
  * NMS Monitoring Metrics, Telemetry, and Incidents
  * Automation Playbooks and Execution Runs
  Engineers and operators collaborate on a single unified network state.
- User-Owned Private Resources (Isolated):
  * Chat Sessions and Message History (queries filtered by session owner_user_id)
  * Personalization Profiles (Persona & Tone)
  * User-Specific Adaptive Memory


6. ADMIN USER ACTIVITY & LIVE SESSION MONITORING
--------------------------------------------------------------------------------
- User Status Engine: Computes status dynamically:
  * DISABLED: Account flag account_enabled is false.
  * ONLINE: Active session with heartbeat within last 120 seconds.
  * SESSION_EXPIRED: Active session present but heartbeat older than 120 seconds.
  * OFFLINE: No active sessions.
- Masked Session Tracking: Active sessions displayed in Admin Control Plane with
  token identifiers masked (e.g. sess_9f2a...81b).
- Targeted & Bulk Revocation: Administrators can revoke any individual session
  or all sessions for a user instantly via DELETE /api/v1/admin/sessions/{id}.
- Security Audit Trail: High-severity events logged to
  operational_user_activity_events (login, logout, session revocation,
  password change, group updates, and account toggle).
